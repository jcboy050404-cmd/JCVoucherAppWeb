## Feature #1 — WhatsApp + Share reminders (fixes the SMS reliability problem)

**Reality check:** A WhatsApp `wa.me/<number>` link works perfectly with a phone number. Messenger `m.me` links need a Facebook *username*, not a phone — so phone-only clients can't be targeted via m.me. The pragmatic solution: **WhatsApp direct (with the client's number)** + **system Share sheet** (covers Messenger/Viber/SMS — user picks the app). `share_plus` is already a dependency.

### Changes — `lib/screens/pppoe_screen.dart`
1. **Add a phone-normalization helper** (local method): convert `09XXXXXXXXX` or `+639XXXXXXXXX` → `639XXXXXXXXX` (international, no `+`, no leading `0`) — the format `wa.me` requires. Falls back to `null` if no valid number.
2. **Fix `_launchWhatsApp`** to accept the phone: build `https://wa.me/<normalized>?text=<encoded>` (currently it omits the number → opens the picker). If no number, fall back to the current picker behavior.
3. **Add `_launchShareReminder(String text)`** using `Share.share(text)` (share_plus) — opens the OS share sheet so the operator can pick Messenger/Viber/SMS/etc.
4. **Update `_showPaymentReminderModal` (line ~246)**: pass `user.phoneNumber` into the WhatsApp launcher, and add a third action button (Share) next to the existing SMS + WhatsApp buttons.

### Optional — `AndroidManifest.xml`
Add `<intent><action android:name="android.intent.action.VIEW"/><data android:scheme="https"/></intent>` to `<queries>` so `wa.me` links resolve on Android 11+. (Minor — the launch still works via externalApplication without it, but this makes `canLaunchUrl` accurate.)

## Feature #2 — Per-voucher Data Limits (proven upsell)

**No service/model work needed** — `addVoucher` already accepts `limitBytes` and sends `=limit-bytes-total=`; `Voucher.limitBytes` + `isExpired` data check + PDF `_formatDataLimit` all already consume it. Only the Generate screen changes.

### Changes — `lib/screens/generate_screen.dart`
1. **State fields** (near line 28–44): add `final _dataLimitNumController = TextEditingController();` and `String _dataLimitUnit = 'None';` (`'None'/'MB'/'GB'`, mirroring `profile_list_screen.dart`). Dispose the controller in `dispose()` (~line 525).
2. **New `_FormCardSection`** "Data Limit" — placed after the Time Limit section (~line 1644). Layout mirrors the profile data-limit UI (`profile_list_screen.dart:200–261`): a numeric `TextFormField` + a `DropdownButton<String>` for None/MB/GB. When unit is `None`, the field is disabled (Unlimited).
3. **Compute `effectiveLimitBytes`** in `_generate()` (near the `effectiveUptime` block, ~line 592): reuse the exact byte math from `profile_list_screen.dart:359–360`:
   ```dart
   String effectiveLimitBytes = '';
   if (_dataLimitUnit != 'None' && _dataLimitNumController.text.trim().isNotEmpty) {
     final val = int.tryParse(_dataLimitNumController.text.trim()) ?? 0;
     if (val > 0) {
       final multiplier = _dataLimitUnit == 'GB' ? 1073741824 : 1048576;
       effectiveLimitBytes = '${val * multiplier}';
     }
   }
   ```
4. **Pass it to `addVoucher`** (line ~652): add `limitBytes: effectiveLimitBytes,` to the call.

That's it — RouterOS enforces the quota natively (`limit-bytes-total`), the voucher list auto-flags exhausted vouchers as expired, and print tickets show "Data: XGB" automatically.

## Feature #3 — Sales Analytics (weekly + 7-day revenue trend)

The dashboard already has `_todaySales`/`_monthlySales`/`_totalSales` getters (line ~385–409) and a chart pattern (`_buildTrafficFlowCard`, LineChart with `fl_chart`). I'll extend, not rebuild.

### Changes — `lib/screens/dashboard_screen.dart`

2. **Add a 7-day daily-revenue aggregator** (helper method): returns `List<FlSpot>` of revenue per day for the last 7 days (bucket `_vouchers` by `activationDate` Y/M/D, sum `price`). Reuse the `fl_chart` `LineChart` pattern from `_buildTrafficFlowCard` (line ~1935).
3. **New card `_buildRevenueTrendCard()`**: a LineChart of the last 7 days' revenue (₱), styled to match the existing traffic flow card (curved line, gradient fill). Place it in both the desktop dashboard home (`_buildDesktopDashboardHome`, ~line 1545) and mobile layout (`_buildMobileLayout` slivers).
4. **Add a "Weekly Income" `StatCard`** to the existing Income & Sales `_statGrid` (line ~2528), and a weekly row to the desktop `_buildSalesMonitoringCard` (~line 1776) — so weekly revenue is visible at a glance alongside Today/Month/Total.

**Caveat (existing behavior, not introduced by this work):** `activationDate` falls back to the generation date (`createdDate`) when a voucher has no `log:` login tag, so revenue may attribute to generation day for never-logged-in vouchers. This is the same basis as the existing today/monthly numbers, so it stays consistent.
